axo — free in telegram and the browser

English through coding

A methodology developed by Arina Bolotbekova that fuses early coding logic with English language acquisition into a single learning loop — an approach with no found precedent in the products surveyed. axo acts as an interactive bridge into English literacy: rather than replacing formal reading, writing, or speech instruction, it builds an intuitive foundation. Children see a word, type the code command, hear it spoken, and watch axo act it out — using action to anchor core vocabulary in memory.

the structure

Two phases, one core loop

phase 01 · learn

Guided introduction

Each word is introduced through visual, auditory, and typing prompts, so the child sees it, hears it, and types it before using it.

phase 02 · challenge

Recall in play

The child recalls and applies vocabulary in interactive play, giving every word an immediate purpose and reason to remember.

the mechanic

One loop, two skills

axo adapts Total Physical Response (TPR) — a proven language-learning method, developed by James Asher, that pairs spoken words with physical actions — and applies it to code. Instead of moving their own bodies, children type commands to control axo. Watching the character carry out their code serves as the physical anchor for new vocabulary.

Market research across leading children's coding and language apps found no precedent for this approach: none of the products surveyed fuses coding mechanics and language acquisition into a single learning loop.

architecture

A real backend, not a static game

axo runs on a Cloudflare Worker at the edge, backed by a D1 (SQLite) database. One Worker does both jobs: it handles the API routes and falls through to static asset serving for everything else — one deploy, one Worker, no separate API host to keep in sync. Secrets, the Telegram bot token among them, live as Worker secrets and never reach the browser.

The split matters: everything in js/ runs in the child's browser and can be read by anyone, so nothing there is trusted. Every decision that gates access is made server-side in the Worker.

auth

Verifying a Telegram session end-to-end

A Telegram Mini App hands the client an initData string. Trusting it as-is would mean anyone could forge a user, so the Worker verifies it cryptographically before acting on who the user is.

HMAC SHA-256 signature over the sorted data-check-string, computed with WebCrypto and compared in constant time
24 hrs Freshness window on auth_date — limits how long a leaked initData string stays useful
20/min Per-user rate limit, applied after signature checks so nobody can drain a real user's bucket

Past the signature, access has gone through two designs. The first asked the Telegram Bot API on every login whether the user was in the axo group, so a bad hour at Telegram locked every family out. The second answers from D1 alone: a single-use access code creates an entitlement, and if the database is unreachable the Worker fails closed — "verification unavailable," not "welcome in." Every rejection logs a one-word reason code for ops, while the client only ever sees a generic error, so failed attempts learn nothing about which check they tripped.

Since 2026-09-24 axo is free, in Telegram and in any browser at play.axolab.space. The code system stays built behind one ACCESS_MODE switch, and the switch fails toward free: anything other than "codes", including unset, means free, because free mode stores nothing about the account — no Telegram ID, name or username. What the Worker keeps instead is anonymous totals, such as new devices and lessons completed, with no IDs.
