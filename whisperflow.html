whisperflow — local voice dictation

Your voice never leaves your machine.

An independent, local alternative to Wispr Flow — the popular cloud-based dictation app — built to answer one question: can you get the same push-to-talk dictation experience without sending your voice to a server? Hold a hotkey, speak, release — text appears at your cursor. Transcription runs entirely on-device via faster-whisper; the only network call in the app's lifetime is a one-time model download on first run. Not affiliated with or endorsed by Wispr Flow.

why local

Replacing the cloud round-trip

Wispr Flow's own pipeline captures audio locally, but sends it to cloud servers for speech recognition and LLM-based cleanup before typing the result back at the cursor — meaning every dictated word transits their servers and requires a constant connection. WhisperFlow replaces the two cloud-dependent stages with local equivalents: on-device transcription via faster-whisper (CTranslate2, CPU int8), and rule-based cleanup for filler words, spacing, and capitalization instead of an LLM call. The one piece deliberately left out of v1 is per-app tone matching, since that's the one stage that genuinely benefits from an LLM.

1 Network call in the app's lifetime — the one-time model download
0 Transcripts ever written to disk — audio held in RAM only
4 Model sizes supported, tiny → large-v3, tuned for CPU-only machines
engineering notes

What building it actually involved

A shutdown race condition with real teeth. The first working version transcribed audio in a background thread and injected the result immediately on completion, with no check for whether the app was still running. Quitting mid-transcription could let a background thread finish after the main process had already exited — at which point focus had returned to whatever window was active, often the terminal. The transcribed text would then get typed into that window. If it's a shell, arbitrary dictated speech gets interpreted as commands. Fixed by guarding the hotkey handlers so no new recording starts once shutdown begins, checking a shutdown flag immediately before text injection, and joining all in-flight worker threads before the process exits — so nothing outlives the window it was meant to type into.

Resource sizing, found the hard way. The larger small Whisper model caused a brief full-system freeze while downloading and loading concurrently over a constrained mobile connection. base runs comfortably faster than real-time on CPU with int8 quantization, and was kept as the practical default — small/medium stay available for machines with more headroom.

A documented security review, not left implicit: every open() and write() call in the codebase was inspected to confirm transcripts are never logged to disk. The clipboard briefly holds dictated text during paste-mode injection — under a second, before the previous clipboard contents are restored — which is disclosed directly in the README rather than glossed over, along with a plain explanation of why the app needs a system-wide keyboard hook to detect the push-to-talk key regardless of which window has focus.

stack

Built with

Python, faster-whisper (CTranslate2, CPU int8 quantization) for on-device transcription, the keyboard library for a system-wide push-to-talk hook, and sounddevice for audio capture. Clipboard-paste or simulated-typing for text injection, selectable in config. Structured around four pieces: a Recorder that captures audio while the hotkey is held, a cleanup pass for filler words and formatting, a text-injection step, and a main loop that loads config, loads the model once, and registers the hotkeys.
