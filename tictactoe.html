tic-tac-toe — real-time multiplayer

Two players, one source of truth.

A Node.js/Express/Socket.io backend running real-time two-player Tic-Tac-Toe over WebSockets. The server holds all game state — the client only renders what it's told, no game logic runs in the browser. Hardened against abuse and audited by a security-reviewer subagent before shipping.

architecture

Server-authoritative by design

The server maintains all game state. When two players connect and both click Find Game, the server pairs them into a named room and creates a game instance for that pair. Move events travel from client to server via Socket.io; the server validates each move, updates state, and broadcasts the result back to both players in the room — the client never decides whether a move is legal, only the server does.

The game engine and matchmaking logic were built as isolated modules with clear interfaces before being wired into the server, making each layer straightforward to reason about independently — and easier to catch the two integration bugs below, since the boundary between "game logic" and "networking" was already clean.

engineering notes

Two real bugs, caught in integration testing

Stale game-state bug. The move handler accepted moves after a game had already ended — winner already decided, or a draw already reached. Fixed by tracking terminal state directly on the game instance and rejecting any move once it's set.

Re-matchmaking race condition. After a game ended normally, the room was never removed from the active-games map — so the matchmaking queue's duplicate-check logic blocked players from starting a new game after clicking Play Again. Fixed by cleaning up the room immediately after emitting the game-over event.

Room cleanup, more broadly. Sockets were never explicitly removed from their Socket.io room after a game ended or a player disconnected, so stale room memberships accumulated on the server across games. Fixed with explicit socket.leave() calls in both the game-over path and the disconnect handler, then verified with a two-client test script confirming each socket could pair into a fresh room after both game-over and opponent-disconnect.

security review

Audited before shipping, not after

A custom Claude Code subagent (security-reviewer) audited the codebase before deployment. It flagged five findings; four were actionable and fixed:

cellIndex Unvalidated input — added explicit type and bounds checking before any move processes
rate limit No cooldown on socket events — added a per-connection timer that rejects moves under 300ms apart
CORS Open by default — locked to a specific origin in production

A fourth fix replaced innerHTML with textContent for rendering server-provided board data, eliminating any XSS risk if that data path ever changes shape. The room-cleanup fix above was itself re-reviewed by the same subagent afterward, which confirmed the cleanup ordering — map deletions before leave calls — was safe with no interleaving window.

hardening

Bounding every resource a client can grow

The audit fixed what was already written. A later pass went after the parts of the server a single client could grow without limit — each one now has a ceiling, and each ceiling is configurable by environment variable rather than hardcoded.

Per-IP connection cap. Socket.io middleware counts live connections per resolved IP and rejects new ones past CONNECTIONS_PER_IP (default 10). Behind a proxy, setting TRUST_PROXY makes it read the real client IP from X-Forwarded-For instead of the proxy's own address. The decrement is bound to the socket's own disconnect event, so a connection can't leak its slot.

Bounded matchmaking queue. The waiting queue is capped at MAX_QUEUE_SIZE (default 100). Past that, the server emits queue-full rather than growing the array — the client is told why it wasn't queued instead of waiting on a pairing that isn't coming.

Feedback on rejection. The rate limiter used to drop fast moves silently, which reads as a broken board. It now emits move-rejected so the client can distinguish "too fast" from "nothing happened." Both limit values are validated at startup and the process refuses to boot on a non-positive or malformed value — a typo fails loudly instead of silently disabling the cap.

stack

Built with

Node.js and Express on the server, Socket.io for real-time bidirectional communication, and vanilla HTML/CSS/JS on the client — no frontend framework, since the client's only job is rendering server-dictated state. No database: games live in memory for their lifetime and are cleaned up on game-over or disconnect.
